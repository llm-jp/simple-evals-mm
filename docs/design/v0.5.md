# simple-evals-mm v0.5 design

Status: agreed 2026-11-01, implemented in steps (see "Plan"). Stored results of v0.4 are not read by v0.5;
`sem convert` audits and converts them once. Terms, file names and CLI follow Harbor (job / dataset / task / trial,
agent, verifier / reward, config.json + lock.json, `job resume`).

## Goals

- One place for each concern. Today the generation loop is copied into every task, the zero-score rule and
  the summary counters are recomputed in four scripts, and checks (history, code hashes) guard files that
  several tools rewrite. v0.5 moves the loop, failure handling, aggregation and file writing into the
  framework; datasets only describe data, prompts and verification.
- Stronger reproducibility with less machinery: pin by git commit, record everything that changes outputs in
  the job config, never store derived values.
- Room to grow: tool use (python in a container), external harnesses (Harbor agents, official model
  harnesses), container environments, a web viewer of model outputs. Generation always produces an ATIF
  trajectory, so all of these plug into the same boundary.

## Concepts

Our terms are Harbor's terms.

| term | meaning |
|---|---|
| job | one configuration (model, settings, commit) and its results, `jobs/<job-name>/`; identity = a UUID in lock.json |
| dataset | a benchmark (ai2d, mmmu, ...) |
| task | one example of a dataset; id = the original id, else a content id (below) |
| attempt | one independent generation of every task of a dataset (`-k`, files `a<k>`) |
| trial | one task x one attempt: one TrialResult (with its ATIF trajectory), trial name `<task_id>__a<k>` |
| agent | how a task is generated: `direct` (one call per turn), `tools` (tool loop), `harbor:<agent>` |
| environment | where tools run: `bwrap`, `apptainer`, `docker`, remote |
| verifier / reward | how a trial is checked (`mcq`, `judge`, rules, execution) and the resulting reward (float or None) |
| metric | how rewards aggregate per dataset (`mean`, `category_mean`, custom) |

Task ids: the dataset's original id when it has one; otherwise `sha256(canonical JSON of the prompt text + sha256
of each image's bytes + answer)[:16]`. Equal ids get `-2`, `-3` in load order (with a warning); the source position
(split, row) is kept in the task data; `load()` asserts uniqueness. The trial meta's task-id fingerprint is over
these ids.

## Components

```
Dataset   load() -> list[Task]; prompt(task) -> Messages; verify(task, trajectory) -> VerifierResult
          multi-turn datasets: next_turn(task, history) -> Messages | None (instead of overriding generation)
          corpus-level datasets (OmniDocBench): verify_all(tasks, trajectories) and a custom metric
Verifier  library: mcq(), judge(template, parse), exact(), boxed(), click_in_box(), rules(...), execute(...)
          a dataset sets `verifier = verifiers.mcq()` or implements verify() itself; the LLM judge is one
          verifier method (`--judge-model`), its raw response is kept in VerifierResult.judge
VerifierResult  reward: float | None, extracted, judge (raw response, model, usage), details (sub-rewards),
          method, cause (error policy)
Metrics   declared per dataset: `metrics = [metrics.mean(), metrics.category_mean()]` (default); aggregation
          applies them to an attempt's rewards (which already follow the error policy); no aggregate() overrides
Agent     run(task, dataset, sampler, env) -> Trajectory (ATIF). v0.5 implements `direct`
Sampler   one class per API format: openai_chat_completions, openai_responses, google_generate_content (default per
          provider: openai / azure -> responses for gpt-5*, else chat; gemini / vertex -> google; others -> chat)
          __call__(messages, tools=None) -> Response(text, reasoning, tool_calls, usage, finish_reason, model,
          provider, system_fingerprint). Model presets (recommended sampling, provider pin, effort levels) are
          registry data, not classes, keyed by exact slugs. In-process HF samplers are removed: local models are served.
ErrorPolicy one table: failure cause -> retry? / verify? / counts in reward?
Retry     Harbor's RetryConfig: `retry: {max_retries (-r), include_causes (default: the policy's retry=yes
          causes), exclude_causes, abort_after_consecutive (circuit breaker, default 20)}` in the job config
Preflight before any trial (like Harbor's _run_preflight): API key variable set, base URL answering GET /models,
          the judge's key / URL when verification runs, datasets loadable; fails fast, names only, never values.
          `--skip-preflight` (recorded in lock.json)
```

Error policy (after Harbor's error classification):

| cause | example | retry | counts in reward |
|---|---|---|---|
| budget_exhausted | finish_reason length, step limit | no | yes, 0 (cut-off answer) |
| refused | provider refusal, content filter | no | yes, 0 |
| context_overflow | input longer than the context | no | yes, 0 |
| provider_failed (transient) | rate limit, 5xx, timeout | yes (`-r`) | no (excluded, `sem runs retry`) |
| endpoint_unavailable | OpenRouter "No endpoints found" / "No allowed providers" / 404, the pinned provider's model-not-found, a served engine refusing connections after every retry | no | no (excluded; circuit breaker) |
| sandbox_failed | container start failure | yes | no |
| judge_failed | judge error / unparseable verdict | yes | no |

## Files

```
jobs/<job>/config.json                  the requested JobConfig (CLI + YAML, resolved defaults)
jobs/<job>/lock.json                    resolved replay inputs: job UUID, package version + commit + dirty / editable,
                                        uv.lock check, dataset revisions + task-id fingerprints + verifier locks, sampler
                                        resolution (provider, api format, key / base-url variable NAMES, request body),
                                        judge resolution, agent, skip_preflight; later server manifest + image digest
jobs/<job>/dirty.diff                   with --allow-dirty: the diff the job ran with
jobs/<job>/images/<sha256>.<ext>        images referenced by trajectories (stored once)
jobs/<job>/<dataset>/trials_a<k>.jsonl  one TrialResult per line (Harbor's shape: id, task_name, trial_name,
                                        task_checksum, agent_info, agent_result {trajectory (ATIF), usage},
                                        verifier_result, exception_info, started_at, finished_at, generation_lock,
                                        verifier_lock); append-only (= checkpoint); frozen when complete
jobs/<job>/<dataset>/trials_a<k>.meta.json   dataset revision, task-id fingerprint, usage, sha256 of the completed file
jobs/<job>/<dataset>/verifier/<verification-id>/a<k>.jsonl   one VerifierResult per line ({task_name, rewards:
                                        {reward}, ...}); a new verification id per verification
jobs/<job>/<dataset>/verifier/<verification-id>/meta.json    judge model + params, verifier lock, commit, sha256 of
                                        the verified trial files and of the result files
jobs/<job>/<dataset>/verifier/current   name of the current verification id
```

`jobs/` is the default (`DEFAULT_JOBS_DIR`, as in Harbor; the PBS scripts moved to `pbs/`). The job name defaults
to the start time `YYYY-MM-DD__HH-MM-SS`; the UUID created with the job is the ATIF `session_id`, the trial name
`<task_id>__a<k>` the `trajectory_id`. Storage is behind `write_trial()` / `iter_trials()`, so Harbor's
one-directory-per-trial layout (with a config.json + lock.json per trial) can replace the packed JSONL later.
No stored aggregates: rewards, std, failure counts and costs are computed from the rows by the declared metrics.
Each trajectory carries `schema_version: "ATIF-v1.8"`; config.json / lock.json carry `format: "sem-job/1"`.
Trajectories contain no absolute paths or secrets.

## Reproducibility

| what | how |
|---|---|
| code | `sem run` starts only from a clean tree (`git status --porcelain --untracked-files=all` empty, no untracked `.py` in the package) and records the commit; `--allow-dirty` stores the diff and marks the job dirty. All package modules are imported at start, so later edits or pulls do not affect a running process. Resume requires the same commit. One shared venv. |
| libraries | installed versions must equal `uv.lock`, else refuse |
| settings | everything that changes outputs is a CLI option or config-file value, recorded in `config.json`; resuming (re-running `sem run` with the same `--job-name`, or `sem job resume`) requires an equal config except `job_name` / `jobs_dir` and runtime-only options (concurrency, retry, verification settings), and the same commit, lock check and dataset digests, else "job directory already exists and cannot be resumed with a different config"; env holds only secrets and machine-local paths / concurrency |
| served engine | `sem serve` writes a manifest: engine version, installed-code hash checked against the wheel RECORD (unregistered edits refused), patches from `serving/patches/<name>/` (name, hash, upstream ref), launch args, model revision, chat-template hash; checked at job start and after server restarts. A different stack = a new job. |
| API models | dated model ids only; per step the response model / system_fingerprint / provider is recorded; a pinned provider mismatch is a failure |
| datasets | revision pinned in dataset code; task-id fingerprint recorded; `sem datasets check` (+ weekly CI) reports newer upstream revisions |
| results | only `run` / `job resume` (trials) and `job regrade` (verifier results) write; both record hashes; `sem job check` verifies them |
| across commits | per-trial `generation_lock` (sha256 of the rendered messages with image content hashes, request params, model / provider / api format, server manifest) and `verifier_lock` (verifier name + params, judge model + params, digest of the verifier code); `sem run --from` reuses, regrades or reruns per trial (step 2) |
| leaderboard | the build refuses dirty jobs, unpushed commits, failed lock checks and unverifiable server manifests; a model row may combine datasets from several jobs (one config per dataset) |

## CLI (`simple-evals-mm`, alias `sem`)

Harbor names where the concept is the same; our own where Harbor's would clash (job vs PBS job, dataset vs HF
dataset) or does not exist.

```
sem run -m PROVIDER/MODEL -d ai2d,mmmu [-c job.yaml] [--job-name NAME] [-k N_ATTEMPTS] [-n N_CONCURRENT]
        [-r MAX_RETRIES] [-l N_TASKS] [-t TASK_ID ...] [-i GLOB] [-x GLOB] [--preset NAME|none] [--effort LEVEL] [--max-output-tokens N]
        [--temperature T] [--top-p P] [--top-k K] [--provider P] [--quantization Q] [--model-arg k=v]
        [--dataset-arg dataset.k=v] [-a AGENT] [--agent-arg k=v] [-e ENV] [--judge-model M] [--generate-only]
        [--base-url U] [--api-key-name VAR] [--api-format F] [-o JOBS_DIR] [--allow-dirty] [--skip-preflight]
        [--print-config] [--dry-run]
sem init                                   write a job config template
sem jobs list
sem job show JOB | table JOBS | check JOB | regrade JOB [-d ...] [--judge-model M]
sem job resume -p JOB [-f/--filter-error-type CAUSE ...]   (-f drops those trials first: retry = resume -f provider_failed)
sem datasets list | download | check
sem models list
sem serve ENGINE MODEL [--patch NAME] ...  launch a server and write its manifest
sem convert OLD_RUN_DIR                    audit + convert a v0.4 run
```

`sem job regrade` also performs the first verification after `--generate-only`. `--dry-run` prints the plan:
datasets, tasks, attempts, trials already done vs to run, the resolved provider / format / variable names and the
resolved settings table (value and source per field; it tries the free catalog / server-info GETs of `prepare()` and
reports `prepare_error` when they fail).

## Inference settings

**max_output_tokens** is the maximum number of generated tokens, reasoning / thinking tokens included, for every
backend. Requests carry it in the API's own field (chat `max_tokens` / `max_completion_tokens`, Responses and Gemini
`max_output_tokens`, sglang / vLLM / hf `max_tokens`), always explicitly: never the server's or API's default (sglang's
default max_new_tokens, vLLM's max_model_len - prompt). No preset sets it. Without `--max-output-tokens` it is the largest
generation the endpoint allows, resolved once at `prepare()` and recorded in lock.json (`settings.max_output_tokens`:
value, requested, endpoint_max, source):

| backend | endpoint maximum |
|---|---|
| OpenRouter | the pinned endpoint's `max_completion_tokens` (`context_length` when null); unpinned (`--preset none` without `--provider`) needs `--max-output-tokens` |
| sglang / vLLM / hf | the server's context length (`/v1/models` max_model_len; hf_server reports the config's max_position_embeddings). The input length is not known client-side: the request sends the context length, the server rejects it with its overflow error (which names the input length) and the request is re-sent once with context - input - 16 (under 256 tokens of room: context_overflow) |
| OpenAI / Azure / Gemini | the preset's `output_limit`, the model's documented output limit (gpt-5.1 128000, gpt-4o 16384, gemini-3.1-pro 65536); Gemini without one: models.get output_token_limit |

A larger `--max-output-tokens` is clamped to the endpoint maximum; both values are recorded. The judge follows the
same rule (a cut-off verdict is judge_failed).

**Every sampling field** (temperature, top_p, top_k, min_p, presence / frequency / repetition penalty), the effort and
max_output_tokens get a value and a source at `prepare()`, recorded in the sampler config (`settings`, in lock.json and
every trial's generation_lock). Precedence:

1. CLI / job config (`--temperature`, `--model-arg`, ...): `cli`
2. the preset: `preset:<name>`
3. defaults the provider / model declares, queried at `prepare()` and then sent explicitly:
   `openrouter:default_parameters` (GET /models; the row's canonical_slug and hugging_face_id are recorded too),
   `model:generation_config.json` (served: the directory the server reports as root, else the HF snapshot in the local
   cache, else the Hub; its sha256 and snapshot revision are recorded), `gemini:models.get`
4. nobody declares it (OpenAI / Azure): not sent, recorded as `provider default (not reported)`

A response that echoes its sampling (the Responses API: temperature / top_p; Chat Completions, OpenRouter and Gemini echo
nothing) is stored per step in `extra.sampling_echo` with the fields that differ from what was sent.

**Presets are exact slugs.** No prefix or wildcard matching: a model released later never inherits settings silently.
Shared settings are families (`samplers/presets.py` FAMILIES) referenced by each exact entry; a served HF id listed in
SERVED_MODELS has the same preset under every engine prefix (sglang / vllm / hf). An unknown slug is refused; `--preset
FAMILY` applies a family to any model id or path (internal checkpoints), `--preset none` runs without model-specific
settings (only the CLI options; max_output_tokens = the endpoint maximum). `--preset` is a job config key (recorded,
compared on resume); `sem models list` shows the exact slugs and the families.

## Endpoint changes and unavailable providers

The endpoint is part of the job identity: `prepare()` records the OpenRouter pinned-endpoint row (provider, tag,
quantization, context_length, max_completion_tokens, canonical_slug) or the served engine's identity (model id, root,
max_model_len, version, generation_config.json digest). These fields and the resolved settings values are compared on
resume (a difference refuses it with the field diff, like the commit) and hashed into every trial's generation_lock;
volatile catalog fields (pricing, uptime) are not.

**Changing provider.** `--provider` / `--quantization` override the preset's pin; they are recorded and make a different
job config, so a different provider is a new job (a resume with them is refused). The leaderboard combines datasets from
different jobs, one config per dataset: finish the unfinished datasets in a new job with the other provider.

**Circuit breaker.** A pinned provider that stops serving the model fails every request with endpoint_unavailable (not
retried) or provider_failed (after retries). When `retry.abort_after_consecutive` (default 20; 0 = off) trials in a row
end in one of these causes, the runner submits no new trials, lets the running ones finish, does not write the failed
trials of that streak or after it (a streak broken by a normal trial is written as it is), and stops with "the pinned
endpoint is failing; resume later with `sem job resume`, or start a new job with another --provider for the unfinished
datasets (`sem job show` lists them)". A plain `sem job resume` regenerates exactly the unwritten trials.

Removed: `--text-only`, `--cot`, `--n-threads`, `--allow-code-change`, `--overlap-repeats` (always on), `runs retry`
(= `job resume -f provider_failed`).

## Converting v0.4 runs

`sem convert` audits instead of copying: verifies `history.jsonl` hashes, finds the commit whose task-file hash
matches the stored provenance, checks per-attempt configs agree, checks task ids against the dataset,
recomputes every aggregate from the rows and re-verifies with the v0.5 verifiers (judge calls cached by request
hash, so unchanged judge prompts cost nothing) and lists reward differences. Result: `legacy-verified`
(shown on the leaderboard as "generated before v0.5") or `legacy-unverified` with reasons (re-run).

## Task ids that changed vs v0.4

v0.5 task ids are the dataset's original id where one exists, else a content id (see Concepts). Where v0.4 stored a
different id, `sem convert` (step 2d) maps the stored rows with this table; every other dataset keeps the v0.4 id.
"row" is the position in v0.4's load order, kept in v0.5 as `task.data["row"]` (with the same source split).

| dataset | v0.4 id | v0.5 id | mapping |
|---|---|---|---|
| realworldqa | row index | content id | by row: `task.data["row"]` == v0.4 id |
| chartqapro | `<row>#<question type>` | content id | by row: the number before `#` == `task.data["row"]` |
| countbenchqa | row index | content id | by row |
| mmlu | row index | content id | by row |
| mmlu_redux | `<subject>/<row>` (row within the subject config) | content id | `task.data["subject"]` + `/` + `task.data["row"]` |
| math | row index | content id | by row |
| simpleqa | row index | content id | by row |
| charxiv | `<arXiv id>#reason` (not unique: charts of one paper share it) | figure id (stem of `figure_path`) | by position: the k-th v0.4 row is the k-th v0.5 task (same order, same filter); `task.data["original_id"]` is the arXiv id |
| gpqa | row index in file order (the options shuffled per row) | Record ID | by row (full runs; a v0.4 `--examples` run indexed its subsample) |
| scienceqa | None | problem id (image directory name) | by row |
| simpleqa_verified | row index | `original_index` | by row |
| multiverse | `<index>#t<k>` (one row per turn) | dialogue index | strip `#t<k>`; the turns of a dialogue become one trial (per-turn rewards in `details["turns"]`) |

### Known v0.4 issues kept for parity

- mmlu: an option cell "None" is read by pandas as NaN and shown as `nan` in the prompt.
- gpqa: v0.4 subsampled (`--examples`) before drawing the option permutations, so a subsampled v0.4 run showed other
  option orders than the full run; v0.5 draws them over the full file (as a full v0.4 run) and selects tasks after.
- JAMMEval: v0.4 loads the subsets unpinned (GitLab main) with a fallback to the public Hugging Face mirror; v0.5 pins
  the GitLab commit v0.4 downloaded and checks every shard's sha256, without a fallback.
- HakushoBench / Heron-Bench: the datasets' category columns are ignored (v0.4 reported no per-category scores).

Server-side keys are not sent: `sem serve` (step 2c) applies them and its manifest is checked against them.
hf_server.py still honours only max_tokens / temperature / effort per request; sampling fields beyond the
temperature (top_p, top_k, repetition_penalty, decode=qwen) reach it in the body but need step 2c to be applied.
Dataset variables (CHARXIV_REASONING_ONLY, LCB_START / LCB_END, JAMMEVAL_*, OMNIDOCBENCH_*) are dataset args.

live tests (`-m network`, `-m api`) stay opt-in.
